« THE ID », COURT, ABRÉGÉ ET LONG — 3 octobre
==============================================

L'ÉCART ANNONCÉ ÉTAIT FAUX. Le relevé du polygone (2 octobre) et les notes de
la 0.7.7 et de la 0.7.8 disaient : « the long id of button 2 » rend « 5 »
dans HC, là où HyperCard rend « card button id 5 of card id … of stack … ».
La seconde moitié n'avait JAMAIS été mesurée : c'était un souvenir, écrit
comme un fait. Mesuré le 3 octobre, HyperCard rend le nombre, comme HC.


MESURÉ DANS HYPERCARD (Basilisk II), par l'utilisatrice
-------------------------------------------------------

Un bouton (id 3) et un champ de carte (id 1) sur une carte de la pile
« test5 », écrit par le script du bouton dans le champ :

    id: 3
    short id: 3
    abbr id: 3
    long id: 3
    card id: card id 2865
    card short id: 2865
    card long id: card id 2865 of stack "Saved HD:More Stacks:Alternate Home Stacks:Home (Small):test5"
    bg id: 2703
    bg long id: 2703
    fld long id: 1

Et deux refus, chacun arrêtant le script :

  · « put the long id of me into x » puis « the name of x » : HyperCard ne
    comprend pas. Une variable qui contient un descripteur ne devient pas un
    objet dans « the … of ».
  · « the long id of this stack » : HyperCard ne comprend pas. Le texte du
    message : non relevé.

Second banc, même jour, deux cartes, x valant « the id of this card » pris
sur la carte 1 ; le champ, recopié par l'utilisatrice :

    card abbr id: card id 2865
    card 2 id: card id 3805
    go x -> card 1
    go card id x -> card 2

  · l'id ABRÉGÉ d'une carte est sa forme par défaut, « card id N » ;
  · une carte qui n'est pas la carte courante se décrit de même ;
  · « go x » ramène sur la carte 1 : le descripteur entier se relit ;
  · « go card id x » ne bouge PAS (on reste sur la carte 2), et la ligne
    suivante s'écrit : le script a continué. L'utilisatrice a vu « expect a
    number here » ; de QUELLE ligne il vient, et s'il est une boîte ou the
    result : non relevé. « card id » n'accepte pas le descripteur entier.

  Conséquence pour HC : plusieurs de nos harnais écrivent « card id » suivi
  de l'id d'une carte — navtest (« card field "data2" of card id
  sortieCarte », « go to card id ident »), pilereelle (« card id n + 0 ») —,
  ce qu'aucune pile d'HyperCard ne peut faire marcher. Ils ne témoignent que
  de l'écart.

  · « send "teste" to y », y valant le long id du bouton : y vaut 3, et le
    gestionnaire « teste » n'écrit rien. HC, même script : « destinataire
    introuvable », PUIS le script continue. Ce que fait HyperCard après
    l'échec — boîte et arrêt, ou silence : non relevé.

Ce qui en ressort :
  · un BOUTON, un CHAMP et un FOND rendent le nombre nu, quel que soit
    l'adjectif ;
  · seule la CARTE se décrit : « card id N » par défaut, le nombre en court,
    et « … of stack "chemin complet" » en long ;
  · une pile n'a pas d'id.

LA CORRECTION — 3 octobre, sur l'accord de l'utilisatrice
--------------------------------------------------------

obj_prop_read (hc_core.c) : l'id d'une CARTE rend « card id N » par défaut
et en abrégé, le nombre en court, « card id N of stack "…" » en long — la
pile écrite comme la met déjà « the long name ». Le reste ne bouge pas.

Le harnais idcarte rejoue les deux bancs ; « go x » y ramène sur la carte 1,
le long id aussi, et « card id (the short id of …) » marche.

Trois harnais écrivaient « card id » suivi de « the id of this card » —
navtest (via navharn, navharn2, navharn3) et pilereelle — : ils passent à
« the short id », comme l'écrirait l'auteur d'une pile d'HyperCard. Trois
témoins changent de la seule forme mesurée (fn, longname, valeur).

Ce qui reste DIFFÉRENT, et voulu ou non mesuré :
  · le CHEMIN de la pile est celui de macOS (« /Volumes/Saved HD/… »),
    comme dans « the long name » depuis qu'il porte un chemin ; HyperCard
    écrivait le chemin à deux-points du vieux Mac OS ;
  · « the long id of this stack » : voir « LA PILE », plus bas.


LA PILE — 3 octobre
-------------------

Le texte du refus, rapporté par l'utilisatrice DANS HYPERCARD, en deux
messages successifs : « can't understand argument of id », puis « can't get
this property ». Lequel vient de quelle tournure — the long id seul, ou un
autre essai — : non relevé. Les deux disent la même chose : refus, et arrêt.

HC rendait 1. Il refuse maintenant toute forme de l'id d'une pile —
« propriété inconnue », dans la langue de ses autres messages — et le
script s'arrête (harnais idcarte, section 5). Les formes courte, abrégée et
nue n'ont pas été jouées dans HyperCard : refusées avec la longue, non
mesurées.


PUSH RECENT CARD, POP CARD INTO — 4 octobre
-------------------------------------------

Venu de la pile d'aide d'Apple, « HyperCard Help », convertie par
l'utilisatrice : whereICameFrom y fait

    push recent card
    pop card into theCard
    return theCard

et cardToStackName en tire le nom de la pile d'où l'on vient. HC répondait
« ne sait pas faire » aux deux lignes.

MESURÉ DANS HYPERCARD (Basilisk II), par l'utilisatrice, pile test6, depuis
un bouton de la carte 3 — go card 1, go card 3, push recent card, pop card
into x :

    pop into : card id 2850 of stack "Saved HD:More Stacks:Alternate Home Stacks:Home (Small):test6"
    carte : 3
    carte 1 : 2850          (the short id of card 1, relevé ensuite)

  · « recent card » est la carte d'où l'on vient ;
  · « pop card into » dépile SANS se déplacer — on reste sur la carte 3 ;
  · le conteneur reçoit le LONG ID, la forme mesurée le 3 octobre.

LA CORRECTION : push reconnaît « recent card » (l'avant-dernière carte de
l'historique, sans y toucher) ; pop accepte into, before et after, et écrit
le long id par container_set, le chemin de « put ». Harnais idcarte,
section 6. « before » et « after » suivent la grammaire de put : NON MESURÉS
dans HyperCard. Ce que fait « push recent card » sans carte précédente : NON
MESURÉ ; HC n'empile rien et rend « No such card ».


CANTMODIFY — 4 octobre, MESURÉ, PUIS CORRIGÉ LE MÊME SOIR
--------------------------------------------------------

La même pile d'aide lit et pose « the cantModify of this stack ». HC :
« propriété inconnue ».

MESURÉ DANS HYPERCARD, pile test6 :

    set the cantModify of this stack to true
    put the cantModify of this stack into v       -- v = true
    put "essai" into card field 1                  -- RIEN : le champ ne change pas
    set the cantModify of this stack to false

  · la propriété se pose et se lit ;
  · une pile verrouillée REFUSE qu'un script écrive dans un champ, EN
    SILENCE : pas de message, et le script continue — « ça s'exécute mais il
    n'y a rien dans le champ ».

La propriété n'est pas venue seule : une propriété qui se lit sans rien
verrouiller serait « le verrou qui ne ferme rien » que hc_core.h refuse pour
cantDelete sur la pile. Elle est donc arrivée AVEC le verrou mesuré, posé aux
deux endroits par où un script écrit dans un champ — v3_ecrit_objet (« put …
into card field 1 ») et la branche « champ » de container_set, où finissent
toutes les écritures par morceau. Refus silencieux, comme dans HyperCard.
Enregistrée dans notre format (« cantmodify », seulement si posée). Harnais
verrou : le banc rejoué, les morceaux, l'aller-retour par le fichier.

NON MESURÉ, DONC NON VERROUILLÉ : une propriété posée, un bouton créé ou
supprimé, la peinture, et la frappe de l'utilisateur dans un champ d'une
pile verrouillée ; le cadenas qu'HyperCard montre dans la barre des menus ;
et le bit du format d'Apple qui porte le verrou — une pile d'origine
verrouillée s'importe libre.
