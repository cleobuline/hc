« HYPERTALK REFERENCE » : LES DÉMONSTRATIONS « RUN THE SCRIPT » — 9 octobre
==========================================================================

La pile d'Apple (version 2.4, convertie par l'utilisatrice) montre chaque mot
du langage par un script que joue le bouton « Run the Script ». Elle n'entre
pas dans le dépôt ; ses gestionnaires sont recopiés dans leur FORME par les
harnais refdemos et runscript.


LE RELEVÉ, DANS LE NOYAU ET NON DANS HC (l'application)
-------------------------------------------------------

Les 136 cartes qui portent une démonstration ont été jouées une par une,
chacune dans un processus à part, par un faux hôte : la souris jamais
enfoncée, « ask » qui répond 5, « answer » qui prend le premier bouton, les
réglages de peinture et les fenêtres tenus comme le fait HCview.m. Ce qui
suit vient de ce relevé, et ne vaut que pour le noyau.

Six démonstrations ont tourné sans fin — if, repeat, repeat while, set,
mouse, scroll : elles attendent un clic, ou un nombre deviné, que le faux
hôte ne donne jamais. Ce n'est pas un défaut.

Ce que le faux hôte ne sait pas faire, et que l'application fait, n'a PAS
été jugé : click, type, drag, doMenu vers l'interface, systemVersion,
clickChunk, clickLine, clickText, clickLoc, screenRect, diskSpace, windows.

« CHAR 1 TO 0 » — MESURÉ, PUIS CORRIGÉ LE MÊME JOUR
---------------------------------------------------

Trouvé en suivant la démonstration clickChunk dans la pile « HyperCard
Help » : sa fonction textToLineNum (attribuée à Ken Laws) écrit

    return the number of lines of char 1 to offset(return & theText & return,
                                                    theContainer) of theContainer

et son commentaire promet 0 quand le texte manque. HC rendait 1 : n2 = 0
voulait dire « pas de fin », et « char 1 to 0 » rendait le premier
caractère. notHelpSuite se trompait donc toujours.

MESURÉ DANS HYPERCARD 2.4.1 (Basilisk II) par l'utilisatrice — les valeurs
contredisent ce que rendait HC, le côté ne fait pas de doute :

    char 1 to 0 of "abc"                                          []
    char 1 to -1 of "abc"                                         []
    word 1 to 0 of "a b c"                                        a
    the number of lines of return                                 1
    the number of lines of char 1 to 0 of (return & "abc" & return)   0

Les caractères et les mots ne suivent pas la même règle. Seuls les
caractères changent (hct_chunk_fin, appelée aux quatre sites qui lisent un
« to » : lecture, put, delete, select). Harnais refdemos, section 4.

NON MESURÉ : les items et les lignes « to 0 » (inchangés : le premier
morceau, comme les mots) ; écrire, effacer, sélectionner dans « char 1 to
0 » — l'écriture laisse la chaîne telle quelle, comme elle le faisait déjà
pour « to -1 », l'effacement n'ôte rien, select pose un point d'insertion.


LA CARTE clickChunk — RÉSOLU : UN CLIC DANS LE VIDE
---------------------------------------------------

Signalé DANS HC (l'application) : la démonstration « coinçait ». La chaîne
des piles d'aide passe entière dans le noyau. La ligne fautive était

    get the clickChunk
    select it

après un clic hors du texte : clickChunk vide, et HC répondait « ne sait
pas faire : select it », qui accuse la syntaxe. L'utilisatrice l'a cherchée
avant de voir qu'elle avait cliqué à côté ; en cliquant sur un mot, tout
remarche. Le message dit maintenant « select : rien à sélectionner, it est
vide », et le script continue comme avant. Ce que fait HyperCard d'un
« select » sur une valeur vide : NON MESURÉ. Harnais refdemos, section 5.


L'EFFET DE BORD DE « char 1 to 0 » SUR LES PILES D'AIDE
-------------------------------------------------------

notHelpSuite répondait toujours faux ; elle répond juste depuis la
correction. Or HyperCard Help lui passe lastItem(":", destination()) et
lastItem(":", <nom long d'une carte>) : avec des chemins en « / », aucune
pile n'est reconnue comme pile d'aide. Mesuré dans le noyau : en quittant
une pile d'aide, closeDownHelpStack retire le menu « Reference » et cesse
d'utiliser HyperCard Help (le menu revient au resumeStack) ; et le bouton
« Go … » de la carte 1 peut paraître. Conséquence de la décision sur les
chemins, ci-dessous ; la correction proposée porte sur la copie convertie de
la pile d'Apple, pas sur HC. Et « the destination » rend chez nous
« stack "/chemin" » : ce que rend HyperCard est demandé.


« set the checkMark of menuItem 4 of menu gHMnu » — 10 OCTOBRE
---------------------------------------------------------------

Signalé DANS HC (l'application) : « hc sait pas faire ça », sur cette ligne
du script de pile de HyperTalk Reference :

    set the checkMark of menuItem 4 of menu gHMnu to TRUEorFALSE

La ligne elle-même marche. Le menu qu'elle vise n'existait pas.

Reproduit dans le noyau, les deux piles chargées, avec la suite de messages
qu'envoie Hcdocument.m (envoiePile) : openStack, puis suspendStack ou
closeStack. HyperTalk Reference fait, dans son openStack,

    start using stack "HyperCard Help"
    pass openStack

et c'est l'openStack de HyperCard Help, atteint par ce pass, qui crée le
menu « Reference ». Le chemin d'un message était figé à l'envoi : le pass ne
voyait pas la pile qu'on venait de mettre en usage, et n'atteignait
personne. Au premier suspendStack ou closeStack, closeDownHelpStack renvoyait
« setCheckMark FALSE » à la pile, et la ligne répondait « menu introuvable ».

Corrigé : la suite de la chaîne, les piles en usage, se relit à chaque pass
(hc_send_args_k_body). Harnais passusage, qui échoue sur le noyau d'avant.

DÉDUIT DU CODE D'APPLE, PAS MESURÉ : sans ce comportement, HyperTalk
Reference ouverte seule n'aurait pas de menu dans HyperCard non plus. Banc
demandé le 10 octobre, à jouer DANS HYPERCARD 2.4.1 (Basilisk II) :

    on mouseUp
      stop using stack "HyperCard Help"
      answer "[" & lastItem(":", "a:b:c") & "]"
      answer "[" & the stacksInUse & "]"
    end mouseUp

    function lastItem
      start using stack "HyperCard Help"
      pass lastItem
    end lastItem

« [c] » au premier dialogue : le pass atteint la pile mise en usage pendant
le gestionnaire, comme HC le fait maintenant. Résultat : EN ATTENTE.

LE MÊME DIALOGUE, PAR LE GLOSSAIRE — le même jour. Une fois Help Extras
lisible (« the textStyle of theChunk », docs/mesures/designateur_calcule.txt),
l'utilisatrice a cliqué un mot du glossaire DANS HC (l'application) : « ça
ouvre, mais toujours le même bug ». Cause, trouvée dans le code et rejouée
dans le noyau par un faux hôte à fenêtres (harnais fenetrepile) : un « go »
vers une autre pile envoyait closeStack à la pile quittée, et l'hôte, dont la
fenêtre passait derrière, suspendStack. Deux départs ; HyperCard Help retire
son menu au premier, et le setCheckMark du second ne le trouve plus. La
référence d'Apple, carte « closeStack » : « If you have more than one stack
open at a time, HyperCard sends suspendStack, not closeStack, when the stack
becomes inactive. » Chez un hôte qui donne une fenêtre à chaque pile, le
noyau laisse maintenant les messages de pile à l'hôte (v3_va_a).

Le faux hôte a montré un second défaut : en passant devant, la fenêtre
reprenait la carte qu'elle montrait, APRÈS que le go eut posé la sienne. Un
second mot du glossaire ouvrait donc la carte du premier. L'hôte passe
maintenant avant. NON VÉRIFIÉ ICI : que les avis de fenêtre arrivent pendant
makeKeyAndOrderFront, comme le faux hôte le suppose. Il faut macOS.

ESSAYÉ DANS HC (l'application) par l'utilisatrice, le même soir, après
recompilation : « ça tourne bien ». C'est le constat d'ensemble, pas une
mesure de l'ordre des avis de fenêtre.

CAS LIMITE, NON TRAITÉ : un « go » vers une pile chargée par « start using »,
qui n'a pas de fenêtre chez HC. cocoa_stack_changed n'y trouve aucun
document : la pile ne venait déjà pas devant, et elle ne reçoit plus non
plus closeStack / openStack du noyau.

CE QUI RESTE. Quitter HyperTalk Reference pour une autre pile (suspendStack)
retire le menu SANS cesser d'utiliser HyperCard Help : removeHelpFunctions
cherche « ":HyperCard Help" & return » dans the stacksInUse, et nos chemins
sont en « / ». Fermer ensuite HyperTalk Reference DE DERRIÈRE, ou quitter HC
quand elle est derrière, renvoie setCheckMark à un menu disparu : « menu
introuvable », encore. C'est la décision sur les chemins, plus bas. Le
second dialogue du banc dit la forme exacte de the stacksInUse dans
HyperCard, retour final compris : sans retour final, HyperCard Help, seule
pile en usage, ne serait pas retirée non plus.

DÉCIDÉ PAR L'UTILISATRICE : PAS DE CHEMINS « Disque:Dossier:Pile »
-------------------------------------------------------------------

Les démonstrations « return » et « offset » coupent « the long name of this
stack » au premier « : » pour trouver le nom du disque, comme sur un Mac
d'époque. HC donne des chemins en « / », et elles affichent « disk named H ».

« Non, on n'imite pas Disque:Dossier:Pile » — l'utilisatrice, le 9 octobre.
Ces deux démonstrations restent donc fausses chez nous, sciemment.
