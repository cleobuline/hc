## Findings

### HC-C2-01 — Signed integer overflow in the WebAssembly GetCardPicture rectangle

- **File:line:** `HC/hc_wasm.c:415-424`, especially line **420**.
- **Severity:** **critical** (undefined integer arithmetic inside a memory-safety validation gate; downstream memory corruption not demonstrated).
- **Status:** **NOT REPRODUCED** — source reasoning only; no malicious WASM module run.
- **Concrete scenario:** A module supplies `g=h=INT32_MIN`, `d=b=INT32_MAX` to `GetCardPicture`. Each computed dimension `l` and `t` is 4,294,967,295, so the product `l * t` overflows signed `int64_t`. The check `l * t > n` itself exhibits undefined behavior. Thus a crafted module can reach the validation with arithmetic for which the C compiler provides no safety guarantee. If optimized code bypasses the intended comparison, a module-provided output buffer reaches `hc_module_peinture` under unchecked dimensions. **This does not establish that the callback actually writes out of bounds; that path must be separately tested.**
- **Suggested fix:** Avoid multiplication until it is proven safe: reject `n < 0` and nonpositive dimensions; compare `l > (int64_t)n / t` before calling the host (or use overflow-checked unsigned multiplication). Apply host drawing-size limits as a second guard.

### HC-C2-02 — Overflow-prone accumulation in text stack loader

- **File:line:** `HC/hc_file.c:909-972` (`acc_line`, `acc_join`, `acc_seg`).
- **Severity:** **high** (potential undersized allocation and out-of-bounds write at extreme cumulative sizes).
- **Status:** **NOT REPRODUCED** — arithmetic inspection; realistic reachability on a 64-bit host not established.
- **Concrete scenario:** An untrusted `.stack` file contains sufficiently many long content/script/paint segments that `a->len + n + 2` wraps `size_t`. The growth loop also doubles `cap` without an overflow test. In that state the capacity check can accept an insufficient buffer, yet `memcpy(a->buf + a->len, s, n)` still writes `n` bytes. Such total input lengths are likely impractical with ordinary available memory, but the parser does not encode this as an invariant.
- **Suggested fix:** Check `n <= SIZE_MAX - a->len - 2` before addition, and `cap <= SIZE_MAX / 2` before each doubling. Propagate overflow as a hard load failure; add a direct accumulator boundary test using controlled lengths.

### HC-C2-03 — Overflow-prone sizing of marshalled WebAssembly parameters

- **File:line:** `HC/hc_wasm.c:1219-1231` (the `lance` argument-size accumulation, near these lines).
- **Severity:** **high** (potential insufficient `hc_boite` allocation with subsequent `depose` write).
- **Status:** **NOT REPRODUCED** — theoretical `size_t` overflow; caller reachability at such cumulative sizes not established.
- **Concrete scenario:** The host passes a very large total of XCMD/XFCN argument strings or window-event strings. `taille += strlen(...) + 1` can wrap before the final `taille > HC_MODULE_PAGES_MAX * 65536` comparison. `calcule` then validates only the wrapped allocation length; `depose` copies the actual argument strings. As on the text loader, a realistic 64-bit exploit has not been established.
- **Suggested fix:** Before each addition, reject when `strlen(s) >= limit - taille` with `limit` set to the permitted module-memory budget; guard `taille <= limit` and any `NULL` inputs.

### HC-C2-04 — Original-stack MacRoman conversion size can overflow

- **File:line:** `HC/hc_origine.c:92-108`, especially line **96**.
- **Severity:** **high** (potential undersized allocation and out-of-bounds writes).
- **Status:** **NOT REPRODUCED** — static reasoning; no path shown that passes an enormous `n` from a real stack.
- **Concrete scenario:** `hc_origine_utf8(octets, n)` allocates `3 * n + 1` bytes without checked multiplication/addition and can output up to three UTF-8 bytes per input byte. If `n > (SIZE_MAX-1)/3`, the allocation size wraps; its conversion loop can overrun the allocation. Whether the original-stack parser admits an `n` this large was not established.
- **Suggested fix:** Return failure before allocating when `n > (SIZE_MAX - 1) / 3`; ensure all callers treat that return as a load failure.

## Useful defenses observed and open verification gaps

- **WASM:** `HC/hc_wasm.c:1027-1057` validates the module-returned `hc_boite` allocation using WAMR before marshalling. Returned string pointers are also checked before reading them; draw callbacks check image and palette length. These guards were **not** reported as bugs.
- **Original-format reader:** `HC/hc_origine.c` uses bounded `Vue` accessors and imposes a 4096-by-4096 upper bound for decoded image dimensions in the examined code.
- **Text-format reader:** embedded module hex input is size-bounded and incomplete module blocks fail loading.
- **Clipboard:** `HC/hc_presse_papiers.c` checks allocations during the inspected copy/paste-clone path. `HC/HCview.m:6919-6938` obtains images from NSPasteboard and delegates decoding to Cocoa; no reproducible native-memory defect was established in that passage.
- **Deferred deletion:** `HC/hc_wasm.c:951-964` bulk-frees modules without an explicit `en_cours` check; nevertheless **a use-after-free cannot be asserted** without tracing whether script-initiated stack destruction is deferred until the active WASM callback finishes. This remains a priority for a targeted lifetime test. Interpreter `HC/hct_*.c` paths were not fully traced.
