# HC — defensive robustness review (October 2026)

**Scope:** first-party HC code only. Review-only; no existing files changed.  
**Repository:** `cleobuline/hc`, default branch `main`.  
**Method:** GitHub source inspection via the connected repository API. No Linux checkout, compiled binary, sanitizer run, fuzzing run, or macOS `xcodebuild` run was available in this review. **No finding below is claimed reproduced.** Line references refer to the inspected version and may move with subsequent commits.

## Findings

### HC-01 — Unchecked size arithmetic while accumulating text-stack records

- **File:line:** `HC/hc_file.c:909-972` (`acc_line`, `acc_join`, `acc_seg`).
- **Severity:** **high** (potential integer overflow and heap overwrite; requires unusually large input/allocation sizes).
- **Status:** **NOT REPRODUCED** — reasoning from the arithmetic only. No test input was constructed or run.
- **Concrete scenario:** A stack from an untrusted source supplies an extremely long sequence of text segments. `a->len + n + 2` (and `a->len + n + 2` saved to `besoin`) is evaluated without first checking `n <= SIZE_MAX - a->len - 2`. Capacity growth with `cap *= 2` is also unchecked. At sufficiently extreme lengths, these operations wrap; the resulting allocation can be too small while `memcpy(a->buf + a->len, s, n)` uses the original `n`, potentially writing outside the allocation. Such a case may require impractically large memory or input on ordinary systems; it is not demonstrated reachable under real limits.
- **Suggested fix:** Before addition, reject if `n > SIZE_MAX - a->len - 2`; before doubling, reject if `cap > SIZE_MAX / 2`. Return a hard load failure on overflow rather than a partially constructed stack. Add a boundary-focused harness using mocked near-`SIZE_MAX` lengths, or direct helper-level tests if possible.

### HC-02 — Unchecked size arithmetic while marshalling WASM arguments

- **File:line:** `HC/hc_wasm.c:1250-1280` (function `lance`, computation of `taille`; line numbers approximate).
- **Severity:** **high** (potential undersized module buffer / out-of-bounds copy if size wraps).
- **Status:** **NOT REPRODUCED** — static reasoning; depends on whether a real caller can supply enough total string bytes to overflow `size_t`.
- **Concrete scenario:** For an XCMD/XFCN invoked with string arguments, the code accumulates `strlen(argv[k]) + 1` into `size_t taille` and checks only the *final* value against `HC_MODULE_PAGES_MAX * 65536`. If the additions wrap, the final bound may pass even though the real strings exceed the allocated `hc_boite` area; `depose()` later copies the real strings using `memcpy`. On 64-bit macOS this requires unrealistically huge combined input unless other call paths can manufacture such lengths, so exploitability is unestablished.
- **Suggested fix:** For each string, compute `len = strlen(s)` and reject when `len >= limit - taille`, using `limit = (size_t)HC_MODULE_PAGES_MAX * 65536` and verifying `taille <= limit` first. Do the same for event strings. This makes overflow impossible independently of platform memory limits.

### HC-03 — Size arithmetic in original-stack text conversion

- **File:line:** `HC/hc_origine.c:92-100` (`hc_origine_utf8`).
- **Severity:** **high** (potential undersized allocation and overwrite if caller can supply extreme `n`).
- **Status:** **NOT REPRODUCED** — the possible overflow is visible, but actual reachability through `hc_origine_lit` or another caller was not demonstrated.
- **Concrete scenario:** `malloc(3 * n + 1)` lacks a check that `n <= (SIZE_MAX - 1) / 3`. With a sufficiently large length the expression wraps and allocates too little space; the loop can emit up to three bytes per input byte. Whether the binary-stack parser can ever pass such an `n` in practice remains open.
- **Suggested fix:** Reject lengths above `(SIZE_MAX - 1) / 3` before allocation; propagate a conversion failure to the loader.

## Examined areas without a qualifying new finding

- **`HC/hc_wasm.c:920-950`**: the formerly unsafe advancement of `pos` in `hc_module_externes` has been addressed. **Do not report that previous bug again.**
- **`HC/hc_wasm.c:385-410` and `470-475`**: callback pixel sizes and bounded return-string copies have explicit guards, and the raw callback registration uses buffer-length signatures. This inspection did **not** establish an out-of-bounds copy at these sites.
- **`HC/hc_origine.c:1120-1200`**: the block directory rejects sizes below the header and sizes past the remaining file (allowing separately documented repairs). No new confirmed OOB read in this portion.
- **`HC/hc_presse_papiers.c`**, the Cocoa paste route, and the object-deletion/deferred-free implementation in `hc_core.c`/`hct_*.c`: **not covered deeply enough** to pronounce safe; no qualifying verified finding is asserted.

## Release decision and testing gaps

**No CRITICAL issue was confirmed by execution in this review.** The three entries above are boundedness concerns, not demonstrated vulnerabilities or crashes. They should be treated as candidates requiring a small targeted harness and sanitizers, not as already reproduced defects.

Recommended verification on an isolated Linux checkout (no source edits committed): `make verifie`, `./tests/lance.sh`, `./tests/lance.sh --asan`, followed by targeted tests at the three arithmetic boundaries. The user-listed prior fixes (parser recursion cap, `calloc` in `appel()`, save failure, `mkstemp`, `ferror` after `fgets`) are intentionally not repeated here.

**Review limitations:** The requested comprehensive study of clipboard deserialization, the Cocoa paste path, and lifetime/UAF paths was not completed. This document therefore must **not** be interpreted as a complete release safety sign-off.
