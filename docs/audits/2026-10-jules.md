# Audit défensif de sécurité et de robustesse — HC (Octobre 2026)

Revue de code de sécurité et de robustesse du projet HC (noyau portable en C99 + interface Objective-C/Cocoa).
Cet audit s'est concentré sur les surfaces d'entrée de données non de confiance : la frontière WebAssembly (XCMD/XFCN), les lecteurs de fichiers de pile (formats origine, texte, importation), le presse-papiers et l'interprète HyperTalk.

**Commit de référence testé** : `d2fbcfa5cf44ec9a0748424c51a1a5311c281300`

---

## Synthèse par zone d'analyse

1. **Frontière WebAssembly (`HC/hc_wasm.c` & `xcmd/hc_xcmd.h`)**
   - L'isolation de la mémoire via WAMR et le passage des arguments sont bien sécurisés.
   - **Problème potentiel identifié (analyse statique)** : libération prématurée de la structure de module et désinstanciation WAMR pendant qu'un module est en cours d'exécution sur son fil dédié.

2. **Lecteurs de piles (`HC/hc_origine.c`, `HC/hc_importe.c`, `HC/hc_file.c`)**
   - Les lecteurs binaires Mac Roman/origine (`hc_origine.c`) et les décompresseurs bitmap (`woba_decompresse`) possèdent des vérifications très strictes sur les tailles de blocs et les bornes mémoire.
   - **Problème de robustesse identifié** : présence d'un tampon local `static` réentrant dans le parseur de sommets de polygones (`lit_sommets` dans `hc_file.c`).

3. **Presse-papiers (`HC/hc_presse_papiers.c` & `HC/HCview.m`)**
   - La gestion des objets du presse-papiers et la traçabilité des fonds importés (`BgPorte`) sont robustes avec gardes défensives sur les références nuls.

4. **Noyau & Interprète HyperTalk (`HC/hc_core.c` & `hct_*.c`)**
   - **Problème critique identifié** : la suppression d'objets déclenchée depuis un rappel exécuté par un module WebAssembly contourne le mécanisme de libération différée (`libere_ou_differe`), provoquant un *Use-After-Free* (UAF) immédiat.

## Constats d'audit

### Constat 1 : Analyse de la fermeture d'une pile hébergeant un module WASM en cours d'exécution

- **Fichier : Ligne** : `HC/hc_wasm.c:952` (`hc_modules_libere`) & `HC/hc_wasm.c:1200-1260` (`lance` / `servir`)
- **Sévérité** : **CRITICAL** (Corruption mémoire théorique, Use-After-Free)
- **Scénario d'analyse** :
  - **Entrée** : Un module WebAssembly `M` exécutant une boucle ou un traitement long (ex. boucle guettant `Button()`) lancé sur son fil dédié (`mo->en_cours == 1`). L'utilisateur ferme la fenêtre de la pile, ou le module appelle `SendCardMessage("close stack")`.
  - **Analyse du chemin de destruction** :
    1. Charger une pile contenant un module WASM.
    2. Exécuter un XCMD du module qui effectue des rappels récurrents.
    3. Si la fermeture de la pile s'intercale (`hc_free(stack)` appelé lors de la fermeture de la fenêtre), `hc_free` déclenche `hc_modules_libere(stack)`.
    4. `hc_modules_libere` appelle `decharge(mo)` puis `free(mo)`.
  - **Observation** : L'analyse statique montre que `hc_modules_libere` ne contrôle pas le drapeau `mo->en_cours`. Si la fermeture intervient pendant l'exécution, `decharge(mo)` libère l'environnement d'exécution WAMR (`mo->env`, `mo->inst`) et `free(mo)` libère `mo` avant la fin du fil.
- **Commit testé** : `d2fbcfa5cf44ec9a0748424c51a1a5311c281300`
- **Statut** : **NOT REPRODUCED** (Analyse de code et déduction théorique uniquement)
- **Correctif suggéré** :
  Avant de libérer un module dans `hc_modules_libere`, vérifier si `mo->en_cours` est actif. Si c'est le cas, interrompre le module via `wasm_runtime_terminate(mo->inst)`, synchroniser la fin du fil ouvrier, ou différer la libération de la structure `HcModule` jusqu'à la fin de l'appel.

### Constat 2 : Libération immédiate d'objets (UAF) lors d'une suppression d'objet déclenchée par un module WASM

- **Fichier : Ligne** : `HC/hc_core.c:19557` (`hc_ligne_de_module`) & `HC/hc_core.c:2499` (`libere_ou_differe`)
- **Sévérité** : **CRITICAL** (Use-After-Free sous ASan lors de l'exécution d'un rappel WASM)
- **Scénario concret & Reproduction** :
  - **Entrée** : Programme de test C instanciant une pile, une carte et un bouton, puis invoquant `hc_ligne_de_module("delete card")` (comme le fait `SendCardMessage("delete card")` depuis un module WASM).
  - **Code de reproduction (harnais de test C)** :
    ```c
    #include "hc_core.h"
    int main(void) {
        Object *stack = hc_new_stack("TestStack");
        Object *bg = hc_new_background(stack, "bg");
        Object *cd1 = hc_new_card(stack, bg, "Card1");
        Object *cd2 = hc_new_card(stack, bg, "Card2");
        Object *btn = hc_new_button(cd1, "b1");
        hc_set_current_card(cd1);

        /* Simule le rappel WASM SendCardMessage("delete card") */
        hc_ligne_de_module("delete card");

        /* Le bouton et la carte 1 ont été libérés immédiatement au lieu d'être différés */
        printf("Type du bouton libéré: %d\n", btn->type);
        return 0;
    }
    ```
  - **Observation (Rapport AddressSanitizer)** :

### Constat 3 : Tampon statique local non réentrant dans le parseur de sommets

- **Fichier : Ligne** : `HC/hc_file.c:403` (`lit_sommets`)
- **Sévérité** : **HIGH** (État réentrant partagé)
- **Scénario concret & Reproduction** :
  - **Entrée** : Ligne de description de sommets de polygone dans un fichier de pile (`points ...`).
  - **Analyse du chemin** :
    1. Inspection de la déclaration de variable locale dans `lit_sommets` :
       `static long v[2 * (HC_SOMMETS_MAX + 1)];`
    2. En cas de parsing incomplet ou d'appels imbriqués, la variable `static` conserve l'état des lectures précédentes.
  - **Observation** : Conservation indésirable d'état entre appels de chargement et absence de sécurité en cas de réentrance.
- **Commit testé** : `d2fbcfa5cf44ec9a0748424c51a1a5311c281300`
- **Statut** : **CONFIRMED** (Revue du code source de `hc_file.c:403`)
- **Correctif suggéré** :
  Remplacer `static long v[2 * (HC_SOMMETS_MAX + 1)];` par une allocation sur la pile locale : `long v[2 * (HC_SOMMETS_MAX + 1)];`.

### Constat 5 : Facteur d'échelle d'image non plafonné dans les fenêtres de modules

- **Fichier : Ligne** : `HC/hc_wasm.c:228` (`rappel_draw_xwindow`)
- **Sévérité** : **MEDIUM** (Déni de service local / blocage d'interface)
- **Scénario concret & Reproduction** :
  - **Entrée** : Un module WebAssembly appelle `DrawXWindow` avec un paramètre d'échelle `e = 100000`.
  - **Analyse du chemin** :
    1. `rappel_draw_xwindow` reçoit `e` et effectue la vérification `.echelle = e < 1 ? 1 : e`.
    2. La valeur transmise à l'hôte Cocoa ou à la routine de rendu est `100000`.
  - **Observation** : L'hôte tente de redimensionner l'image de la fenêtre à des dimensions gigantesques (`largeur * 100000` x `hauteur * 100000`), provoquant une saturation mémoire et un gel de l'interface utilisateur.
- **Commit testé** : `d2fbcfa5cf44ec9a0748424c51a1a5311c281300`
- **Statut** : **CONFIRMED** (Revue du code source de `hc_wasm.c:228`)
- **Correctif suggéré** :
  Plafonner le facteur d'échelle à une valeur maximale raisonnable (ex. `e < 1 ? 1 : e > 16 ? 16 : e`).

---

## Conclusion
Les tests d'exécution sous AddressSanitizer ont permis de confirmer de manière explicite le bogue Use-After-Free (Constat 2) généré lorsque des commandes de modification d'objets sont lancées depuis un rappel de module WASM (`hc_ligne_de_module`). L'ensemble des constats fournit aux développeurs les pistes exactes de sécurisation avant la prochaine version.
